# 从进程到 epoll：补基础的讲义

> 目标：读完能用自己的话讲清楚——一个线程怎么同时服务一千个连接。
> 读法：按节读，每节末尾的“检查点”答不上来就回头再看一遍。

---

## 0. 一个故事贯穿全文

两台程序：

- **客户端**：`nc 127.0.0.1 9102`，发一句话；
- **服务器**：`epoll_echo`，收到什么回什么，同时服务很多客户端。

我们要搞清楚的，就是这两句话从键盘到网卡、再到对方屏幕，中间经过哪些东西。

## 1. 进程、内核、fd

### 1.1 进程手里只有“号码”

你的程序里：

```c
int listen_fd = socket(...);   /* 返回 3 */
```

`3` 只是一个整数。**真正的 socket 对象在内核里**，你的进程只拿到一个编号。

```
进程（用户态）                     内核（内核态）
┌──────────────┐                 ┌──────────────────────┐
│ fd 0 → 终端   │                 │                      │
│ fd 1 → 终端   │   fd 表         │  socket 对象          │
│ fd 2 → 终端   │ ──────────────► │   ├ 状态             │
│ fd 3 → ???    │                 │   ├ 本地地址/端口     │
└──────────────┘                 │   ├ 对端地址/端口     │
                                  │   ├ 接收缓冲区        │
                                  │   ├ 发送缓冲区        │
                                  │   └ 等待队列          │
                                  └──────────────────────┘
```

**fd 表是每个进程一张**，0/1/2 默认是 stdin/stdout/stderr。

### 1.2 系统调用是唯一的门

进程不能直接碰内核对象，只能“请内核帮忙”：

```
read(fd, buf, n)   → 进入内核 → 从 socket 接收缓冲区拷 n 字节到 buf
write(fd, buf, n)  → 进入内核 → 把 buf 拷进发送缓冲区，协议栈负责发出去
accept(...)        → 进入内核 → 从等待队列取一个连接，造一个新 socket 对象
```

每次系统调用都要**从用户态切换到内核态**，有成本（几百纳秒到几微秒）。

### 1.3 关键认知

> **fd 是句柄，不是对象。** 你 `close(3)`，只是删掉表项；对象是否销毁看引用计数（还有没有别的 fd 指着它）。

**检查点**：为什么 `close(3)` 之后，3 这个号码可能马上被新连接复用？

## 2. 一条 TCP 连接是什么

### 2.1 四元组

```
客户端 IP:端口  ←→  服务器 IP:端口
127.0.0.1:47804      127.0.0.1:9102
```

这四个数唯一确定一条连接。服务器端口固定，客户端端口由内核随机分配（临时端口）。

### 2.2 三次握手由内核完成

```
客户端内核                    服务器内核
    │ ── SYN ────────────────► │
    │ ◄─ SYN + ACK ─────────── │
    │ ── ACK ────────────────► │   连接建立
```

**注意**：握手完成时，服务器**应用进程**还没参与。连接已经躺在内核的 `accept 队列` 里，等你的程序 `accept` 来取。

### 2.3 监听 socket vs 连接 socket

```
监听 socket（LISTEN）
   ├─ 绑定 9102
   ├─ 不传数据
   └─ 只负责“收新连接”
          │
          │ accept()
          ▼
连接 socket（ESTABLISHED）
   ├─ 绑定 9102 + 对端 47804
   ├─ 有收发缓冲区
   └─ 数据都走它
```

**每 accept 一次，就多一个连接 socket。**

**检查点**：1000 个客户端连上来，内核里有多少个 socket 对象？

## 3. 服务器的五个动作

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);   /* 1. 造对象，拿句柄 */
bind(fd, 地址);                              /* 2. 绑定 IP:端口 */
listen(fd, backlog);                         /* 3. 变成监听 socket */
int c = accept(fd, ...);                     /* 4. 取一个连接，得到新 fd */
read(c, ...); write(c, ...);                 /* 5. 收发数据 */
close(c);                                    /* 6. 关闭，释放 */
```

每一步对应的内核变化：

| 动作 | 内核里发生了什么 |
|---|---|
| `socket` | 分配 socket 对象，fd 表加一项 |
| `bind` | 给对象记上本地地址 |
| `listen` | 状态改为 LISTEN，创建等待队列 |
| `accept` | 从队列取一个连接，新建对象，返回新 fd |
| `read` | 从接收缓冲区拷数据到用户态 |
| `write` | 从用户态拷到发送缓冲区，协议栈异步发 |
| `close` | 引用计数减一，归零则销毁 |

**检查点**：`read` 是从网卡读，还是从内核缓冲区读？

## 4. 最朴素的服务器：一连接一线程

```c
while (1) {
    int c = accept(...);              /* 阻塞：没连接就睡 */
    pthread_create(处理 c 的线程);     /* 新线程负责这条连接 */
}

/* 每个线程里 */
while ((n = read(c, buf, ...)) > 0) {  /* 没数据就睡 */
    write(c, buf, n);
}
```

```
主线程 ──accept──┬──► 线程 1 ──read/write── 连接 A
                 ├──► 线程 2 ──read/write── 连接 B
                 └──► 线程 3 ──read/write── 连接 C
```

问题：

- 1000 连接 = 1000 线程，每个线程有栈（默认 8MB 虚拟内存）；
- 线程切换要进内核，开销大；
- 大部分时间线程都在睡（等数据），却占着资源。

**检查点**：为什么“线程在睡”也算成本？

## 5. 非阻塞：把“等”变成“问”

把连接设成非阻塞：

```c
fcntl(fd, F_SETFL, flags | O_NONBLOCK);
```

行为变化：

| | 阻塞 | 非阻塞 |
|---|---|---|
| 没数据 `read` | 睡着等 | 立刻返回 -1 + `EAGAIN` |
| 队列空 `accept` | 睡着等 | 立刻返回 -1 + `EAGAIN` |

于是可以“问一圈”：

```c
for (每个连接) {
    if (read(fd, ...) > 0) 处理;
}
```

问题：**没有数据时也在空转**，CPU 100%。连接越多，空转越费。

**检查点**：`EAGAIN` 是错误吗？

## 6. epoll：让内核替你看

### 6.1 三个系统调用

```c
int ep = epoll_create1(0);                    /* 建一个“名单本” */
epoll_ctl(ep, EPOLL_CTL_ADD, fd, &ev);        /* 登记：帮我盯 fd */
epoll_wait(ep, events, 64, -1);               /* 等：谁有事告诉我 */
```

### 6.2 内核里有什么

每个 epoll 实例：

```
┌────────────────────────────────────┐
│ 红黑树（关注列表）                  │
│   fd 3 → {关注可读, 便签 3}         │
│   fd 5 → {关注可读, 便签 5}         │
│                                    │
│ 就绪链表（谁有事）                  │
│   fd 5                              │
│                                    │
│ 等待队列（谁在 epoll_wait 睡觉）     │
└────────────────────────────────────┘
```

### 6.3 事件是怎么产生的

```
网卡收到数据
  → 硬件中断
  → 驱动放进内存（DMA）
  → 协议栈解析，挂到 socket 接收队列
  → 调用“数据就绪”回调
  → 找到所有监视这个 socket 的 epoll
  → 把对应条目挂进“就绪链表”
  → 唤醒正在 epoll_wait 的线程
```

**全程没有轮询。** 没人发数据时，一点 CPU 都不烧。

### 6.4 epoll_wait 返回什么

```
就绪链表： [fd 5]
   ↓ 拷贝
events[0] = { events=EPOLLIN, data.fd=5 }
返回 n = 1
```

`n` 是**事件数**，不是连接数。

### 6.5 为什么快

| 方案 | 每次要做的事 |
|---|---|
| select | 把 fd 集合拷进内核，内核遍历所有 fd |
| poll | 把数组拷进内核，内核遍历所有 fd |
| **epoll** | 登记一次；内核只在“有事”时把就绪条目给你 |

复杂度从 O(总 fd 数) 变成 O(就绪数)。

**检查点**：epoll 自己会去读 socket 里的数据吗？

## 7. 用这个模型重读 epoll_echo

### 启动

```c
socket → 3；bind；listen；非阻塞
ep = epoll_create1() → 4
add_fd(ep, 3)          名单：{3}
```

### 客户端来连接

```
内核完成握手 → 连接进 accept 队列 → 3 号 fd 可读
epoll_wait 返回 1：events[0] = {data.fd=3}
fd == 3 → 进入 accept 分支
accept → 5 → 非阻塞 → add_fd(ep,5)    名单：{3,5}
accept → -1 EAGAIN → 停
```

### 客户端发数据

```
内核：5 号 socket 收到数据 → 回调 → 就绪链表加 5
epoll_wait 返回 1：events[0] = {data.fd=5}
fd != 3 → read(5) → 拿到字节 → write(5) 回显
read 再调用 → EAGAIN → 退出内层循环
```

### 客户端关闭

```
客户端发 FIN → 5 号 socket 可读（EOF）
epoll_wait 返回 1：events[0] = {data.fd=5}
read(5) → 0 → closed = 1
epoll_ctl(DEL) + close(5)              名单：{3}
```

### 全景图

```
                ┌─────────────────────────────┐
                │ 启动：socket/bind/listen     │
                │ epoll_create1 + 登记 listen  │
                └──────────────┬──────────────┘
                               ▼
                  ┌─────────────────────────┐
        ┌────────►│ epoll_wait  （睡）       │
        │         └────────────┬────────────┘
        │                      │ 有事件
        │                      ▼
        │         ┌─────────────────────────┐
        │         │ events[i].data.fd = ?    │
        │         └───────┬─────────┬───────┘
        │             ==listen    !=listen
        │                 │         │
        │                 ▼         ▼
        │          accept 循环    read 循环
        │          新 fd 登记     回显/关闭
        │                 │         │
        └─────────────────┴─────────┘
```

## 8. 十个常见误解

1. ❌ “fd 就是 socket” → ✅ fd 是句柄，对象在内核
2. ❌ “accept 会把数据拷过来” → ✅ 只取连接，返回新 fd
3. ❌ “epoll 会读数据” → ✅ 只通知可读，读还得自己 `read`
4. ❌ “epoll_wait 返回连接数” → ✅ 返回事件数
5. ❌ “read 返回 0 是错误” → ✅ 对端关闭（FIN）
6. ❌ “监听 fd 也要 accept 才能读数据” → ✅ 监听 fd 从不读数据
7. ❌ “注册一次就永远有效” → ✅ close 会自动移除
8. ❌ “一个 fd 只能进一个 epoll” → ✅ 可以进多个
9. ❌ “epoll 能盯普通文件” → ✅ 普通文件永远可读，会被拒绝
10. ❌ “阻塞 socket 放进 epoll 也没事” → ✅ 读的时候会卡死整个循环

## 9. 自测 12 问

1. fd 是什么？对象在哪？
2. 一个进程有几张 fd 表？
3. `listen` 和 `accept` 返回的 fd 有什么区别？
4. 三次握手是谁完成的？
5. 连接建立后，数据先到哪？
6. `read` 从哪读？`write` 写到哪？
7. 阻塞 `read` 没数据会怎样？非阻塞呢？
8. `EAGAIN` 是错误吗？
9. epoll 实例里有哪些结构？
10. 事件是怎么被 epoll 知道的？（轮询还是回调）
11. `epoll_wait` 的返回值是什么？
12. 为什么一个线程能服务一千个连接？

### 答案

1. 进程内的编号；socket 对象在内核。
2. 一张（每个进程一张）。
3. listen 只接客；accept 返回的是具体连接，用来读写。
4. 两端内核，不需要应用参与。
5. 内核里该 socket 的接收缓冲区。
6. 用户态缓冲区 ↔ 内核 socket 缓冲区。
7. 阻塞会睡；非阻塞立刻返回 -1 + EAGAIN。
8. 不是，表示“暂时没有”。
9. 红黑树（关注）、就绪链表、等待队列。
10. 回调/中断，不是轮询。
11. 就绪事件个数。
12. 因为 epoll 只把“有事的 fd”报给它，其余时间线程在睡。
